# Integration Test Standard

> A decision document, not a tutorial. For unit tests (what "unit" means, the Source Rule, the
> coverage tiers) see [UNIT_TEST_STANDARD.md](./UNIT_TEST_STANDARD.md).
>
> Kerf has no database and no external services, so "integration" here means the **medium** and
> **large** tests: several packages together, golden outputs, random edits, timing, and the app in a
> browser.

---

## 1. The kinds of test and when to write each

| Kind | Command | What it proves | Lives in |
| --- | --- | --- | --- |
| Golden | `pnpm test:golden` | The reference projects produce exactly the numbers in the spec | `packages/fixtures/tests/golden/` |
| Property | `pnpm test:prop` | An invariant holds for 1,000 random valid edits | `packages/fixtures/tests/prop/` |
| Stress | `pnpm test:stress` | Hostile or huge input is bounded, reported and finishes | `packages/fixtures/tests/stress/` |
| Benchmark | `pnpm bench` | A time budget from the spec holds | `packages/fixtures/tests/bench/` |
| Cross-package | `pnpm test` | Packages agree at their boundary (core with io, for example) | `packages/fixtures/tests/unit/` |
| End-to-end | `pnpm e2e` | A real person's flow works in a real browser | `packages/app/e2e/` |

Write one when **any** of these is true:

- The spec states a number or behaviour that users will rely on (**golden**).
- A rule is meant to hold for *every* input, not just the ones you thought of (**property**).
- The spec sets a budget (**benchmark**).
- Two packages meet and neither can import the other, so neither can test the seam alone
  (**cross-package**).
- It is a step of the core flow in the Interaction spec (**end-to-end**).

Do **not** write a medium test for pure logic that a unit test already pins exactly. Medium tests
are slower; do not use them to re-prove a single function.

### Pyramid

About 70% unit, 20% medium, 10% end-to-end. A target, not a law: while a milestone adds goldens, the
middle layer will be heavier.

## 2. The Beyonce Rule, for Kerf

> If you liked it, you should have put a test on it.

If a user's cut list, sheet count or dimension would change when your code changes, a test must pin
it. "The spec says so" is not protection; a failing test is. When a PR changes something the spec
states numerically, ask: *if this broke silently, would any existing test catch it?* If not, add the
test in the same PR.

When reviewing, check the same thing.

## 3. Golden tests

- **Inputs are hand-authored** `project.json` files (see `packages/fixtures/README.md`), with
  stable hard-coded ULIDs. They contain intent only and use expressions where the spec uses
  parameters.
- **Expected outputs are copied from the spec**, not generated by the code. Each length carries a
  `_spec` entry with the fraction the spec prints; an ordinary integrity test checks the integer
  equals it.
- **Never edit a golden to make a test pass.** See the `FIXTURE:` process in the Unit standard,
  Section 10.
- Compare the **whole output** with `toEqual`. Do not spot-check fields of something the spec
  specifies fully.
- Stable ids that the spec leaves open (for example a generated match-set id) are normalized before
  comparing, with a comment saying why.
- Where the spec gives no number, **assert nothing** and record the gap in
  `packages/fixtures/README.md` ("Not specified, so deliberately absent"). Do not invent one.

---

## 4. Property tests

- **Name the invariant**, taken from the Domain model's invariant list or the Build plan harness
  (for example "mirroring never changes a cut-list line").
- **Run the code.** The test must call the function under test; an edit that is never evaluated
  proves nothing. Assert at least one thing that can only be true if the code ran.
- Use valid edits from `packages/fixtures/src/edits.ts`. Add an arbitrary there rather than
  inlining a new one.
- 1,000 runs is the project standard (`RUNS`). Do not lower it to make a test faster; make the code
  faster.
- When fast-check reports a failure, copy the shrunk counterexample into a plain unit test (a
  regression example) before fixing.
- Make "does not throw" strict: assert there is **no `internal-error` diagnostic**, otherwise the
  safety net hides the bug.

---

## 5. Benchmarks

- Written as timing **tests**, so they use the same milestone mechanism as everything else.
- The budget is the spec's number (solve under 100 ms, nesting 100 parts under 1 s). Record the
  measured baseline in a comment beside it.
- A benchmark that is within 25% of its budget is a warning sign; note it in the PR.
- Never merge a milestone with a failing benchmark (Build plan, "What agents should not do").

---

## 6. End-to-end tests

- Written first against the contract of labels and test ids in
  `packages/app/e2e/bookcase.spec.ts`. Visible text is **shop language** from the Interaction spec;
  the banned UI words (mesh, vertex, face, component, instance, material, extrude, boolean) never
  appear in an assertion.
- Use accessible roles and labels (`getByRole`, `getByLabel`); use `data-testid` only for repeated
  items such as cut-list lines.
- No fixed sleeps. Rely on Playwright's auto-waiting.
- One flow per file. The bookcase flow is the acceptance test for the Charter's question 1.
- Gate with `test.fail(!isMilestoneActive('M4'))` while the milestone is inactive.

---

## 7. Milestones, expected failures and the audit

Tests for a milestone that is not built yet are written first and fail on purpose.

- **Vitest:** `milestone('M2', 'name', () => { ... })`. While `milestones.json` has `M2: false`, it
  runs as `test.fails`: CI stays green and turns red if the test passes early.
- **Playwright:** `test.fail(!isMilestoneActive('M4'))`.
- **Activating** a milestone is flipping its entry in `milestones.json`, in the acceptance PR.

`test.fails` has a hole: a test that fails for the *wrong* reason (a typo, a bad import) also
"passes". Close it with the **audit**, run before declaring any milestone done:

1. Set every milestone to `true` temporarily.
2. Run the whole suite and read each failure.
3. Every failure must be `NotImplemented` (or a documented missing input such as the `.skp` files).
4. Restore `milestones.json`. Do not commit the temporary flags.

Constant-only assertions never go under `milestone()`: they pass today, and an unexpected pass
fails the run. Put them in an ordinary test.

---

## 8. Isolation and determinism

- No shared mutable state. Fixtures are read-only; helpers return copies.
- No network, no wall clock, no unseeded randomness. Time budgets are the one use of a clock.
- Output must not depend on the machine: no time zone, locale, or file-system order. (`.kerf`
  files are stamped with a fixed ZIP epoch for this reason, and a test pins it.)
- Temporary files, if any, go in a fresh directory per test.

---

## 9. Independent review

**Every milestone, without exception** (maintainer ruling), run an independent review before it is declared done. The reviewers must not have seen your reasoning:

| Reviewer | Question |
| --- | --- |
| Spec correctness | Where does the code disagree with the spec or the ADRs? |
| Silent failure | What can go wrong without a diagnostic? What input can crash or hang it? |
| Test quality | What is untested? Which tests are vacuous or derived from the code? |

Findings become **failing tests first**, then fixes. Record the outcome (verdict, findings, what
was done) in the PR description, and in `docs/reviews/` when the findings changed a decision.
Run a second pass after the fixes; the first round of fixes produced new defects in M1.

---

## 10. CI

CI runs, in order: lint (Biome, dependency-cruiser, license headers), typecheck, unit, golden,
property, benchmarks, end-to-end. A milestone PR is done when its acceptance tests pass in CI and
the audit in Section 7 is clean.

## 11. Quick reference

```
Number stated in the spec?         golden test, expected value copied from the spec
Must hold for every input?         property test; it must actually run the code
Has a time budget?                 benchmark test with the spec's number
Two packages, one seam?            cross-package test in packages/fixtures/tests/unit
Part of the core flow?             Playwright, shop-language labels
Milestone not built yet?           milestone() / test.fail(), then run the audit
Spec gives no number?              assert nothing, record the gap
Changed a fixture?                 FIXTURE: commit, with reason, reviewed
```
